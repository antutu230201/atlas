4. 先记录基线，再改代码。只有测量或页面验收发现明显问题时才调整视觉；优先复用 `packages/tokens` 和 `packages/ui`，不写死颜色/间距/字号，不为改 UI 引入未经说明的依赖。

## 优先级与实施项

### P0：笔记主列表虚拟化

**状态：**2026-11-08 已完成（分支 `codex/note-list-virtualization`）。回收站未改动，见下方“未做”。

**目标：**避免最多 100 篇笔记卡片及其正文预览同时进入 DOM，同时保留自然页面滚动和现有展开/删除/回收站流程。

**建议改动：**

- 先检查 `modules/sample-note/src/index.ts` 的 `list`、`listTrash` 数据排序和 100 条上限，再检查 `modules/sample-note/src/web/list-page.tsx`、`trash-page.tsx` 的真实渲染负载。
- 先虚拟化主列表；回收站只有在测量或结构显示同样有明显 DOM 负担时再做，不为了对称而增加复杂度。
- 待办模块已使用 `@tanstack/react-virtual` 3.14.24。若笔记模块也采用，依赖应归属于笔记模块，不能从笔记模块导入待办模块代码；说明模块级依赖的体积、MIT 许可和自写替代方案。不要把依赖提升到全站共享包，除非至少有两个模块确实需要统一抽象。
- 动态行高须使用实测；正文展开/收起、窗口缩放、筛选（若新增）后重新测量。列表项提供正确的 `aria-posinset` / `aria-setsize`，键盘可到达可视列表项操作；保留焦点，不让滚动重排丢失焦点。
- 不改变笔记的数据模型、软删除或跨 workspace 权限，不扩大 API 返回上限来“喂给”虚拟列表。

**验收：**用 100 条长短混合笔记（含空正文、长正文、展开项）验证首屏/末尾挂载节点数、滚动位置、展开、删除、恢复、键盘访问；在 390px 和桌面宽度验证无横向溢出。至少补充 Playwright 覆盖；若需要辅助纯函数/虚拟器测试，再按已有 Vitest 工作区补测试。

**验收证据（2026-11-08）：**

- 实现：[list-page.tsx](../../modules/sample-note/src/web/list-page.tsx) 使用 `useWindowVirtualizer` + `measureElement` 实测行高，`overscan: 6`、`gap: 12`；空正文、短正文、280 字预览、展开长正文四类行都在同一列表内混合。
- 依赖：`@tanstack/react-virtual` 3.14.24（MIT、headless）只加到 `modules/sample-note/package.json`；未提升到共享包，也未从待办模块导入代码。
- 用例：[note-module.spec.ts](../../apps/web/e2e/note-module.spec.ts) 用 100 条 mock 数据测得挂载行数 390px 首屏 8 / 末尾 11、1280px 9（均 < 30）；`aria-posinset` 首行 1、末行 100；展开后行高实测变大且不与下一行重叠，收起后恢复；键盘删除发出正确 id、列表变 99 且焦点留在列表内；390px / 1280px 无横向溢出；回收站恢复仍正常。
- 门禁：`pnpm typecheck` 16/16、`pnpm lint`、`pnpm test` 10/10（API 111 项）、`pnpm format:check`、`pnpm --filter @atlas/web build` 通过；app-shell / note / todo 三个 E2E 4/4 通过。
- 未做：回收站页仍全量挂载（未测量出明显负担，按计划不为了对称而改）；该路由尚无 Lighthouse 与发布环境数据。

### P1：应用页面无障碍与 UI 一致性审计

**目标：**覆盖实际应用页面，而非只检查 Storybook 组件。

**页面范围：**注册/登录、根大屏、待办、笔记及回收站、习惯、听歌统计、AI 助手、通知、设置/审计。优先检查最近改动最多和包含复杂交互的页面。

**检查维度：**

- 亮色/暗色、390px/1280px；键盘 Tab/Shift+Tab、方向键、Enter、Escape；焦点可见、焦点顺序合理、弹层关闭后焦点归还。
- 表单标签/错误关联、按钮名称、图表替代文本、动态状态播报、对比度、缩放与横向溢出。
- 每个数据查询至少区分加载、空数据、请求失败和刷新失败；危险操作有可撤销或二次确认；成功/失败反馈一致。
- 业务 UI 只使用设计令牌与组件库。对每个缺陷记录路由、主题、视口、复现步骤、严重度和截图/测试证据，再修复高优先项。
- `pnpm a11y` 是 UI Storybook 门禁，保留它；若要对应用页面做 axe 自动扫描，先确认现有 `axe-core` 在 Web E2E 中是否可复用。确实需要新依赖时，先说明体积、许可证和替代方案，再加到正确的 devDependency。

**验收：**严重/关键 axe 问题为零；主要页面没有键盘陷阱；已覆盖的亮暗主题和手机视口没有溢出；加入可重复的自动检查或明确记录无法自动化的人工验收项。

### P2：性能基准更新与热点修复

**目标：**把“减少卡顿”变为可比较指标，按数据定位热点，不做猜测式全站重构。

- 使用生产构建测 `/register`、`/`、`/m/todo_notes/list`、`/m/sample_note/list`、`/m/dashboard/listening`、`/assistant`、`/notifications`、`/settings`。至少跑移动端与桌面端；记录 FCP/LCP、TBT、CLS、JS 传输体积和路线的测试环境。
- 路线图已有历史记录：本机 `/register` 曾测到移动端性能 100、LCP/FCP 0.9s、TBT 20ms。这是旧版本的本机数据，不代表现在或生产。重新测并与历史数据区分。
- 数据压力测试采用隔离数据库。覆盖通知 10 万行已有路径，并补笔记/待办的合理数据量；同时观察 SQL 执行、API 负载、响应字节、DOM 挂载数与滚动期间长任务。禁止把压力数据或个人数据写入正式库、日志、截图或夹具。
- 只有在热点证据明确时才改查询/缓存/动画；租户过滤、RLS、权限、审计及事件语义不得为速度绕过。

**验收：**保留可复制的测量命令、机器/浏览器/构建说明、数据量和结果；每个修复前后有同口径对比。达不到目标时写明瓶颈和后续方案，不编造“已优化”。

### P3：全站功能与体验缺口清单

完成 P1 页面走查后，把问题按“用户影响 × 使用频率 × 实施风险”排序。优先修复数据丢失/状态误导、核心操作失败、移动端阻塞和权限/租户问题；其次才是新功能和视觉微调。每项功能要有用户故事、验收条件、加载/空/错状态、权限、审计影响和测试，不提前改数据库字段语义或做大范围重构。

可能的审查点（须先从现有代码验证，不能直接当成缺陷）：

- 笔记/通知/审计记录到上限后的分页、排序和数据导出完整性。
- 离线体验目前是否有 service worker、缓存策略和冲突处理；涉及用户数据的离线缓存需另列隐私/安全决策，不默认缓存敏感数据。
- 全站文案的翻译表现状。若尚无统一 i18n，先提案和范围，不在本轮零散引入平行翻译框架。
- 重要操作的撤销/恢复、批量操作、失败重试是否一致，新增功能是否遵循模块公开 API 和事件总线。

## 每项任务的交付门禁

1. 代码改动前阅读对应 ADR，列文件、数据模型（没有则注明无）、风险和验收标准。
2. 最小范围实施；业务能力放在模块，不让模块互相导入；输入有 schema、查询有 workspace 过滤、写操作符合审计/软删除规则。
3. 新逻辑同步测试，关键流程有 Playwright；运行 `pnpm typecheck`、`pnpm lint`、`pnpm test`、`pnpm format:check`，改 Web 时跑 `pnpm --filter @atlas/web build`；改应用 E2E 时跑相关 Playwright spec。
4. 在浏览器实际走查亮/暗、手机、键盘、空态和错误态。未实际检查的项目明确标为未验收。
5. 更新本计划/`docs/roadmap.md` 和用户文档；必要时增加 ADR。每一项独立 Conventional Commit，最终汇报测试通过数、剩余风险和未完成项。
