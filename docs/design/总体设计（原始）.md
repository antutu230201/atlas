# 个人长期成长型系统：总体设计与 Agent 开发提示词全集

Oct 30, 2026 · @tutu

## 一、产品定位与核心理念

先做一个稳固、可长期生长的“个人平台内核”，再把你的各种需求做成可插拔模块逐个加上去；内核稳，模块才能无限加，整套能力最终也才能打包出售。

你没有指定具体业务方向，所以本方案按“平台 + 模块”设计，不绑定行业。第一个模块用什么，到阶段 3 再定；如果你已有明确方向，只需替换阶段 3 的提示词，其余全部复用。

**三层目标**

| 层次 | 对应阶段 | 目标 | 判断标准 |
| --- | --- | --- | --- |
| 自用 | 阶段 0–3 | 每天都想打开，数据完全属于你 | 你自己连续使用两周不想换工具 |
| 打磨 | 阶段 4–6 | 体验、AI、质量达到可对外展示的水平 | 首屏 < 1.5 秒，核心操作 < 100 毫秒反馈 |
| 售卖 | 阶段 7–8 | 多租户、计费、授权、文档、官网齐备 | 一个陌生人能自助注册、付费、使用 |

**“顶级”的六条衡量标准**

1. 快：首屏 < 1.5 秒，列表滚动 60fps，任何操作都有即时反馈。
2. 一致：所有界面共用一套设计令牌和组件，不允许出现“风格不同的页面”。
3. 可扩展：新增一个功能 = 新增一个模块，不需要改内核代码。
4. 可靠：数据不丢，全部可导出，可备份，可恢复。
5. 安全：默认最小权限，密钥不进代码库，所有输入都校验。
6. 可演进：有测试、有文档、有架构决策记录，三个月后的你和 Agent 都看得懂。

这六条会原样写进总纲提示词，Agent 每次开发都要对照。

## 二、总体架构

系统分四层：业务功能只存在于“模块”这一层，其余由平台提供，内核永远不需要知道有哪些模块。

&#91;embedded content: 总体架构 · 四层，12 项内核能力\]

读图自上而下：用户看到应用外壳，外壳动态挂载已启用模块的页面；模块通过模块协议接入内核；内核再通过适配器使用数据库、缓存、存储和外部服务。

**五个关键设计**

1. 模块即插件：每个模块用 manifest 声明权限、依赖、路由、菜单、设置和数据迁移；安装、启用、停用都不改内核代码，停用后数据保留。
2. 租户隔离：所有业务表带 workspace\_id，应用层按它过滤，数据库行级安全再兜底一层。现在只有你一个租户，将来每个客户就是一个租户。
3. 事件驱动：模块之间不互相调用，只发布和订阅事件；事件先落库再投递，服务重启不丢。
4. 适配器隔离外部依赖：支付、邮件、AI 模型、存储都隔着接口，换供应商只改配置。
5. 商业化预留：套餐、额度、特性开关、审计日志从内核起就存在，业务代码只问“有没有权限”，不关心用户买了什么套餐。

**核心数据实体**

| 实体 | 作用 | 关键字段 |
| --- | --- | --- |
| 用户 user | 登录身份，可属于多个工作空间 | 邮箱、认证方式 |
| 工作空间 workspace | 租户，数据隔离边界 | 名称、套餐、品牌设置 |
| 成员 membership | 用户在某个工作空间中的角色 | user\_id、workspace\_id、角色 |
| 模块安装 module\_install | 某工作空间启用了哪个模块的哪个版本 | workspace\_id、模块名、版本、状态 |
| 权益 entitlement | 套餐赋予的功能与额度 | workspace\_id、特性键、额度 |
| 事件 event | 模块间通信记录，保证不丢 | 类型、版本、内容、投递状态 |
| 审计 audit\_log | 所有写操作的记录 | 操作者、对象、变更前后 |

## 三、技术选型与工程规范

默认选 TypeScript 全栈单仓库：前后端共用类型，Agent 改一处就能编译期发现全链路的错误，长期维护成本最低。技术名称集中写在总纲的一段里，想换栈只改那一段，其余提示词不动。

| 层 | 默认选型 | 选它的理由 | 可替换为 |
| --- | --- | --- | --- |
| 单仓库 | pnpm + Turborepo | 多包共享代码，增量构建快 | Nx |
| 前端 | Next.js（App Router）+ React + TypeScript | 生态最大，SSR 与 SPA 都能做 | Vue 3 + Vite |
| 样式与组件 | Tailwind CSS + Radix UI 基元 + 自建组件库 | 无障碍好，设计令牌易落地 | 其他 headless 组件库 |
| 前端数据 | TanStack Query + Zustand | 服务端状态与本地状态分开 | Pinia 等 |
| 后端 | NestJS（模块化、依赖注入） | 天然契合“模块即插件” | Fastify、Spring Boot |
| 数据库 | PostgreSQL + Drizzle ORM | 关系 + JSON + 向量（pgvector）一库多用 | MySQL |
| 缓存与队列 | Redis + BullMQ | 异步任务、限流、会话 | 云厂商队列 |
| 文件存储 | S3 兼容对象存储 | 本地可用 MinIO 开发 | 云厂商 OSS |
| 认证 | 邮箱 + OAuth + Passkey，RBAC 权限 | 为多用户和售卖预留 | 自建或托管认证服务 |
| 计费 | Stripe（海外）/ 国内聚合支付 | 订阅、试用、发票齐全 | 按目标市场选 |
| 测试 | Vitest + Playwright | 单元、集成、端到端三层 | Jest |
| 交付 | Docker + GitHub Actions | 一键本地起、一键部署 | 其他 CI |
| 可观测 | OpenTelemetry + Sentry + 结构化日志 | 线上问题能定位 | 云厂商方案 |

**目录结构**

```text
/
├─ apps/
│  ├─ web/            前端应用
│  ├─ api/            后端服务
│  └─ docs/           用户文档站
├─ packages/
│  ├─ ui/             设计系统与组件库
│  ├─ tokens/         设计令牌
│  ├─ core/           平台内核（事件总线、模块注册、权限）
│  ├─ sdk/            模块开发 SDK 与类型
│  └─ config/         共享的 lint、tsconfig
├─ modules/           业务模块，每个模块一个目录
│  └─ <module-name>/  manifest + server + web + migrations + tests
├─ docs/
│  ├─ adr/            架构决策记录
│  └─ roadmap.md      路线图与当前阶段
└─ AGENTS.md          总纲提示词
```

**工程规范（写进总纲，Agent 必须遵守）**

- 一个任务一个分支，一个提交只做一件事，提交信息用约定式格式。
- 每个功能必须带测试：核心逻辑单元测试，关键流程端到端测试。
- 所有接口输入用 schema 校验，所有数据库变更走迁移文件，禁止手改库。
- 密钥只放环境变量，仓库里只提交 `.env.example`。
- 每个重大选择写一页架构决策记录，放 `docs/adr/`。
- 每个阶段结束必须更新 `docs/roadmap.md` 和用户文档。

## 四、设计系统与体验标准

“顶级外观”靠的是一套被严格执行的设计系统，而不是某一页做得好看：先定令牌和组件，再允许写页面，页面里不允许出现任何写死的颜色、间距或字号。

| 维度 | 标准 |
| --- | --- |
| 设计令牌 | 颜色（含语义色：成功、警告、危险、信息）、字号阶梯、间距（4px 基数）、圆角、阴影、层级、动效时长与曲线，全部定义在 `packages/tokens`，一处改全站变 |
| 主题 | 亮色、暗色、跟随系统；预留“品牌主题”接口，将来买家可换自己的品牌色与标志 |
| 组件 | 按钮、输入、选择、表格、表单、弹窗、抽屉、提示、标签页、空状态、骨架屏、命令面板；每个组件有全部状态（默认、悬停、聚焦、禁用、加载、错误）并带示例页 |
| 动效 | 过渡 150–250 毫秒，只用于传达状态变化；尊重“减少动态效果”系统设置 |
| 交互 | 全局命令面板（Cmd/Ctrl+K）、完整键盘操作、撤销与重做、拖拽排序、乐观更新、批量操作 |
| 无障碍 | 达到 WCAG 2.2 AA：对比度、焦点可见、语义标签、屏幕阅读器可用 |
| 响应式 | 手机、平板、桌面都可完整使用，不是“能缩小”而是重新布局 |
| 性能预算 | 首屏 JS 压缩后 < 200KB；LCP < 2 秒；长列表虚拟滚动 |
| 国际化 | 所有文案走翻译表，默认中文与英文，日期、数字、货币按地区格式化 |
| 内容与空态 | 每个空列表、错误、加载都有设计过的文案与引导，不出现裸白屏与技术报错 |

**视觉方向的做法**：不要让 Agent 凭空“做得好看”。先让它按阶段 1 的提示词产出 2–3 套视觉方向（只含令牌与五个核心组件），你挑一套，之后全站锁定。以后想换风格，只改令牌即可。

## 六、总纲提示词（项目宪法）

用法：在仓库根目录新建 `AGENTS.md`（Claude Code 用 `CLAUDE.md`，内容相同），把下面整段原样放进去。之后每个阶段的提示词都不用重复这些背景，Agent 每次开工都会先读它。

```text
# 项目宪法：个人平台（代号 Atlas，可改名）

## 1. 你的角色
你是这个项目的首席工程师兼产品设计师。你的交付标准是“可以直接卖给付费客户的商业产品”，而不是演示或原型。遇到取舍时，永远优先：正确 > 可维护 > 体验 > 速度。

## 2. 产品愿景
这是一个“平台内核 + 可插拔模块”的系统。内核提供：账号与权限、工作空间（租户）、模块注册与生命周期、事件总线、统一数据访问、通知、搜索、AI 能力层、设计系统。所有业务功能都以“模块”的形式存在，新增功能不得修改内核。
目标分三层：自用 → 打磨 → 对外售卖（多租户、订阅计费、授权、白标）。现在写的每一行代码，都要为将来售卖留出空间，但不要提前实现用不到的东西。

## 3. 技术栈（集中在此，换栈只改这一节）
- 单仓库：pnpm + Turborepo
- 前端：Next.js（App Router）+ React + TypeScript + Tailwind CSS + Radix UI 基元
- 前端数据：TanStack Query（服务端状态）+ Zustand（本地状态）
- 后端：NestJS + TypeScript
- 数据库：PostgreSQL + Drizzle ORM，迁移文件管理，向量用 pgvector
- 缓存与队列：Redis + BullMQ
- 文件：S3 兼容对象存储
- 测试：Vitest（单元与集成）+ Playwright（端到端）
- 交付：Docker + GitHub Actions
- 可观测：OpenTelemetry + Sentry + 结构化日志

## 4. 六条质量标准（每次交付都要对照）
1. 快：首屏 < 1.5 秒，核心操作 < 100 毫秒反馈，长列表虚拟滚动。
2. 一致：只使用 packages/tokens 的设计令牌和 packages/ui 的组件，禁止写死颜色、间距、字号。
3. 可扩展：新增功能 = 新增模块，不改内核。
4. 可靠：数据不丢，所有数据可导出，所有写操作可审计。
5. 安全：默认最小权限；所有输入用 schema 校验；密钥只在环境变量；防注入、防越权、防重放。
6. 可演进：有测试、有文档、有架构决策记录（docs/adr/）。

## 5. 架构铁律
- 模块之间不得直接引用对方代码，只能通过事件总线或内核提供的公开接口通信。
- 每个模块是独立目录：manifest（名称、版本、权限、依赖、路由、菜单、设置项）+ server + web + migrations + tests。
- 所有业务表必须带 workspace_id（租户隔离），所有查询必须按它过滤；用数据库行级安全作为第二道防线。
- 所有写操作记录审计日志（谁、何时、对什么、改了什么）。
- 删除默认软删除，并提供回收站与恢复。
- 对外只暴露带版本号的接口（/v1/...），破坏性变更必须升版本。
- 任何外部服务（支付、邮件、AI 模型、存储）都经过适配器接口，方便替换。

## 6. 工作流程（每个任务都按此执行）
1. 先读 docs/roadmap.md 和本任务相关的 ADR，说明你理解的目标与范围。
2. 先给出简短的实施计划（文件改动清单、数据模型变化、风险），等我确认后再动手；我说“直接做”时可跳过确认。
3. 小步实现：一个任务一个分支，一个提交只做一件事，提交信息用约定式格式。
4. 同步写测试：核心逻辑有单元测试，关键用户流程有端到端测试。
5. 自己运行：类型检查、代码规范检查、全部测试必须通过，再宣布完成。
6. 自己验收界面：在浏览器里实际操作一遍，检查亮色、暗色、手机宽度、键盘操作、空态与错误态。
7. 更新文档：docs/roadmap.md、用户文档、必要的 ADR。
8. 用下面的格式向我汇报。

## 7. 完成的定义（缺一项就不算完成）
- 功能按验收标准全部可用，且没有已知严重缺陷。
- 类型检查、规范检查、测试全部通过，新增代码有测试覆盖。
- 界面只用了设计令牌和组件库，亮暗主题、响应式、无障碍检查通过。
- 有加载态、空态、错误态，文案走翻译表。
- 数据库变更有迁移文件且可回滚。
- 文档与 roadmap 已更新。

## 8. 禁止事项
- 禁止为了“先跑起来”绕过类型、校验、权限或测试。
- 禁止引入未经说明的新依赖；需要新依赖时说明理由、体积、许可证、替代方案。
- 禁止在没有我同意时做大范围重构、改目录结构、改数据库已有字段含义。
- 禁止把密钥、令牌、个人数据写进代码、日志或测试夹具。
- 禁止编造“已完成”：没运行过的东西不能说通过了；做不到的要直说。
- 禁止一次提交混入多个不相关改动。

## 9. 汇报格式
- 做了什么（3–5 行）
- 如何验证（我可以复制执行的命令或操作步骤）
- 测试结果（通过数量、覆盖的关键流程）
- 偏离计划的地方与原因
- 遗留问题与建议的下一步
```

## 七、分阶段开发提示词

使用方法：严格按阶段顺序，一次只发一个阶段给 Agent。每个阶段的提示词都默认 Agent 已读过 `AGENTS.md`。上一阶段的验收没通过，不要进入下一阶段。你需要把方括号里的内容按自己情况替换。

### 阶段 0：脚手架与工程基线

```text
【阶段 0：脚手架与工程基线】
先完整阅读 AGENTS.md。本阶段只搭骨架，不写任何业务功能。先给我实施计划，确认后再动手。

任务：
1. 初始化 pnpm + Turborepo 单仓库，按 AGENTS.md 建立 apps/、packages/、modules/、docs/ 目录。
2. 配置 TypeScript 严格模式、ESLint、Prettier、提交前检查（husky + lint-staged）、约定式提交校验。
3. 编写 docker-compose，包含 PostgreSQL、Redis、MinIO；一条命令 pnpm dev 启动全部服务。
4. apps/api 提供 GET /v1/health，返回服务、数据库、Redis 的状态；apps/web 做一个首页占位并成功调用该接口。
5. 建立 Drizzle 迁移体系和第一个迁移；环境变量用 schema 校验，启动时缺失即报错；提供 .env.example。
6. 跑通一个 Vitest 示例测试和一个 Playwright 示例测试。
7. 编写 GitHub Actions：安装、类型检查、规范检查、测试、构建，并启用缓存。
8. 写 docs/roadmap.md（阶段 0–8 与当前进度）、docs/adr/0001-tech-stack.md、README（本地启动步骤）。

验收标准：
- 全新机器克隆仓库后，按 README 不超过三条命令即可跑起全部服务。
- 访问 web 首页能看到后端健康状态。
- 类型检查、规范检查、测试、构建在本地与 CI 全部通过。
- 提交历史清晰，每个提交只做一件事。
```

### 阶段 1：设计系统

```text
【阶段 1：设计系统】
目标：建立全站唯一的视觉与交互基础，之后所有页面只能用它。

第一步（先不要写完整组件库）：
基于“专业、克制、高级、长期耐看”的产品气质，给我 3 套视觉方向。每套包含：亮色与暗色色板（主色、中性色阶、语义色）、字体搭配（中英文）、圆角与阴影风格、动效风格、一句话气质描述。用 Storybook 或独立展示页，把同样的五个组件（按钮、输入框、卡片、表格行、弹窗）在 3 套方向下并排展示，并附亮暗两种主题。完成后停下，等我选定一套。

第二步（我选定后）：
1. packages/tokens：颜色、字号阶梯、间距（4px 基数）、圆角、阴影、层级、动效时长与曲线，输出为 CSS 变量与 Tailwind 配置，支持亮色、暗色、跟随系统，并预留“品牌主题覆盖”接口。
2. packages/ui：按钮、图标按钮、输入框、文本域、选择器、开关、复选与单选、标签、徽标、卡片、表格（排序、选择、虚拟滚动）、表单（含校验提示）、弹窗、抽屉、下拉菜单、提示气泡、消息提示、标签页、分页、面包屑、骨架屏、空状态、加载指示、命令面板外壳。
3. 每个组件覆盖全部状态：默认、悬停、聚焦、按下、禁用、加载、错误，并写用法文档。
4. 配 Storybook，并接入 axe 无障碍检查与 Playwright 视觉回归截图。
5. 做一个“设计系统自身的示例应用页”，展示所有组件的亮暗主题。
6. 写 docs/adr/0002-design-system.md，说明令牌命名规则和如何新增组件。

验收标准：
- 令牌是全站唯一来源：在 apps 与 modules 中全局搜索，不得有写死的十六进制颜色或像素间距。
- 所有组件通过 axe 检查，键盘可完整操作，焦点可见。
- 切换主题无闪烁，减少动态效果设置被尊重。
- 视觉回归测试基线已建立。
```

### 阶段 2：平台内核

```text
【阶段 2：平台内核】
目标：做出“新增功能只需新增模块”的地基。先给我数据模型与模块协议的设计（含 ER 图或表结构说明），确认后再实现。

任务：
1. 账号与认证：邮箱密码（安全哈希）、OAuth 登录、Passkey、会话管理、邮箱验证、找回密码、登录限流与异常登录提醒。
2. 工作空间（租户）：创建、切换、邀请成员；角色为所有者、管理员、成员、访客；基于权限点的 RBAC；所有业务表带 workspace_id，并启用数据库行级安全作为第二道防线。
3. 模块系统：定义 manifest 的 schema（名称、版本、所需权限、依赖、路由、菜单项、设置项、数据迁移目录）；支持注册、启用、停用、依赖解析；模块迁移按模块独立执行；前端路由与菜单由已启用模块动态挂载；每个模块有自己的设置页。
4. 事件总线：发布订阅，使用 outbox 模式保证不丢，支持重试与死信，事件有版本号与类型定义。
5. 审计日志：所有写操作记录谁、何时、对什么、改了什么，并提供查询界面所需的接口。
6. 通知中心：站内通知 + 邮件适配器（先实现本地开发用的邮件捕获）。
7. 统一设置与特性开关：用户级、工作空间级、系统级三层。
8. 任务队列与定时任务：基于 BullMQ，带重试与可观测。
9. 文件服务：上传、下载、预览、病毒扫描接口预留，签名链接。
10. packages/sdk：模块开发 SDK 与类型；并写《如何开发一个模块》文档，要求按文档能在 30 分钟内做出一个最小模块。

验收标准：
- 写一个只含一个页面、一张表的“示例模块”，不改动内核任何代码即可安装、启用、停用，停用后菜单与路由消失、数据保留。
- 越权测试：用户 A 无法读取或修改工作空间 B 的任何数据（接口层与数据库层各一组测试）。
- 事件总线在服务重启后不丢事件；审计日志覆盖全部写接口。
- 全部测试通过，核心包测试覆盖率不低于 80%。
```

### 阶段 4：体验打磨

```text
【阶段 4：体验打磨】
目标：把“能用”打磨成“用着舒服，让人愿意截图分享”。

任务：
1. 全局命令面板（Cmd/Ctrl+K）：可搜索页面、数据、操作；模块可注册自己的命令；支持最近使用与快捷键提示。
2. 全局搜索：基于 PostgreSQL 全文检索，模块通过接口把可搜索内容注册进来，结果按模块分组，支持中文分词。
3. 导入导出：每个模块必须能导出为通用格式（JSON 与 CSV），并能导入；工作空间级别可一键完整导出与恢复。
4. 性能：做一次性能审计。用 Lighthouse 与真实数据量（造 10 万条数据）测试，修复首屏体积、请求瀑布、重复渲染、长列表卡顿；把性能预算写进 CI，超标即失败。
5. 动效与反馈：为状态变化加入克制的过渡动画；所有异步操作用乐观更新并支持失败回滚；加入骨架屏而不是转圈。
6. 离线与弱网：断网时界面可读，写操作排队，恢复后同步，并给出清晰提示。
7. 无障碍复查：用屏幕阅读器走通核心流程，修复所有问题，达到 WCAG 2.2 AA。
8. 文案与国际化：检查所有文案，统一语气与术语，补齐中英文，日期、数字、货币按地区格式化。
9. 做一份《体验走查报告》：对所有页面逐页检查，列出问题与修复结果。

验收标准：
- 命令面板能在 100 毫秒内给出结果；10 万条数据下列表滚动保持流畅。
- Lighthouse 性能、无障碍、最佳实践均 ≥ 95。
- 任意模块的数据都能导出并在新工作空间导入恢复。
- 体验走查报告中无未解决的高优先级问题。
```

### 阶段 5：AI 能力层

```text
【阶段 5：AI 能力层】
目标：让 AI 成为平台的内置能力，而不是外挂的聊天框；并保证成本可控、数据安全、可替换模型。先给我设计方案，确认后实现。

任务：
1. 模型适配器：统一接口封装多个模型供应商，支持流式输出、工具调用、结构化输出、超时与重试、降级到备用模型；供应商密钥由工作空间管理员配置，加密存储。
2. 上下文与检索：基于 pgvector 为各模块数据建立向量索引（模块通过接口声明哪些字段可被索引），实现带权限过滤的检索，保证 AI 绝不会读到用户无权访问的数据。
3. 工具注册：模块可以向 AI 注册“工具”（例如“创建待办”“查询笔记”），AI 调用工具时走和用户一样的权限与审计；所有有副作用的操作必须先让用户确认。
4. 助手界面：全局侧边助手，可引用当前页面与选中内容；支持对话历史、重新生成、复制、反馈（有用/无用）。
5. 模块内嵌 AI 功能：提供 SDK，让模块能以几行代码接入“总结、改写、分类、提取、问答”。至少给第一个模块接入两个真实有用的 AI 功能。
6. 用量与成本：记录每次调用的模型、令牌数、费用、耗时；工作空间级别的额度与限流；管理界面可查看用量。
7. 安全：防提示词注入（外部内容与指令隔离）、输出过滤、敏感信息脱敏、关闭 AI 的总开关。
8. 评测：建立一组固定的评测用例与自动评分脚本，每次改动提示词或模型都要跑，防止质量倒退。

验收标准：
- 换一个模型供应商只需改配置，业务代码零改动。
- 越权测试：AI 无法检索或操作用户无权访问的数据。
- 有副作用的工具调用没有用户确认就不会执行。
- 用量统计与实际账单误差 < 2%；评测脚本在 CI 中可运行。
```

### 阶段 6：质量与安全加固

```text
【阶段 6：质量与安全加固】
目标：达到“可以放心让陌生人把重要数据放进来”的水平。本阶段不加新功能。

任务：
1. 安全审计：按 OWASP Top 10 与 OWASP ASVS 逐项检查，输出《安全审计报告》并修复；包括注入、越权、跨站脚本、跨站请求伪造、服务端请求伪造、文件上传、会话固定、密码与令牌存储、速率限制、依赖漏洞扫描（接入 CI）。
2. 数据保护：敏感字段加密存储；日志脱敏；制定数据保留与删除策略；实现“账号注销并彻底删除数据”流程。
3. 备份与恢复：数据库每日自动备份与保留策略；写一份恢复手册并实际演练一次，记录恢复耗时。
4. 可观测性：接入链路追踪、错误上报、结构化日志；建立核心指标看板（请求耗时、错误率、队列积压、数据库慢查询）；为关键故障配置告警。
5. 测试加固：补齐端到端测试覆盖全部核心流程；加入负载测试（目标：100 并发用户下核心接口 P95 < 300 毫秒）；加入混沌测试（数据库或 Redis 中断时的行为）。
6. 可靠性：幂等接口、重试与熔断、优雅停机、数据库连接池与慢查询治理。
7. 依赖与许可证：生成依赖清单与许可证报告，确认没有与商业售卖冲突的许可证。
8. 代码健康：清理重复代码与死代码，补齐 ADR，更新所有文档。

验收标准：
- 安全审计报告中无未修复的高危与中危问题。
- 恢复演练成功，记录的恢复时间满足你设定的目标（建议 < 1 小时）。
- 负载测试达标；故障注入测试下系统能降级而非崩溃。
- 许可证报告通过，CI 含漏洞扫描与许可证检查。
```

## 八、与 Agent 协作的方法

阶段 8 之后，系统靠下面四条常备提示词长期生长：加模块、评审、重构、复盘。每一次改动都走同一个小循环，系统就不会越做越乱。

### 常备提示词 A：新增一个模块

```text
【新增模块】[模块名]
先读 AGENTS.md、docs/roadmap.md 与《如何开发一个模块》。
我要解决的问题：[一句话]
核心对象与关系：[列出]
典型使用场景：[2–3 个]
先输出需求说明（用户故事、数据模型、权限点、事件、首页小组件、AI 工具、导入导出格式），确认后按 modules/<name> 的标准结构实现。
硬性要求：内核零改动；只用设计系统组件；带空态、加载态、错误态；带导入导出；带搜索注册；带端到端测试；带用户文档；按 AGENTS.md 的完成定义自检并汇报。
```

### 常备提示词 B：代码与体验评审

```text
【评审】范围：[某个模块或某次改动]
请你换成一位严苛的外部评审，不要为已有实现辩护。从以下角度逐项检查，每项给出“问题、严重程度、证据（文件与行号或截图）、修复建议”：
1. 是否违反 AGENTS.md 的架构铁律与禁止事项
2. 安全与越权风险
3. 性能与数据量放大后的表现
4. 设计系统一致性（有无写死样式、重复组件）
5. 无障碍与键盘操作
6. 测试缺口与脆弱测试
7. 文案、空态、错误态
先只输出评审报告，不要改代码；我确认哪些修复后你再动手。
```

### 常备提示词 C：重构

```text
【重构】目标：[例如：拆分过大的组件 / 统一数据请求方式]
约束：不改变外部行为；每一步都保持测试全绿；分成多个可单独回滚的小提交。
步骤：1) 先补齐缺失的测试，锁定现有行为；2) 给出重构计划与风险；3) 确认后分步执行；4) 对比重构前后的体积、复杂度、性能；5) 更新 ADR。
如果发现需要改变外部行为，立即停下来问我。
```

### 常备提示词 D：每周复盘

```text
【每周复盘】
对照 docs/roadmap.md，总结本周完成项、未完成项与原因；列出技术债清单并按“影响 × 修复成本”排序；检查依赖漏洞与过期依赖；检查测试时长与 CI 稳定性；基于用量与错误数据，给出下周最值得做的三件事及理由。输出为 docs/weekly/YYYY-MM-DD.md。
```

### 避免失控的七条规则

1. 一次只给一个阶段或一个任务，验收通过再继续；不要一次布置“把整个系统做完”。
2. 每次都要求先出计划，你确认后再写代码；计划里出现你看不懂的东西，就让它换成人话解释。
3. 永远让 Agent 自己运行测试并贴出结果；你自己抽查：真的打开界面点一遍。
4. 保持提交小而清晰，出问题随时可回滚；每个阶段结束打一个版本标签。
5. 会话变长、Agent 开始遗忘或重复时，让它先把进展写进 `docs/roadmap.md`，然后新开会话，以 `AGENTS.md` + roadmap 作为起点。
6. 重大决定（换库、改数据模型、改定价）必须写 ADR，并由你亲自拍板。
7. 想法很多时先记进 `docs/ideas.md`，每周复盘时统一排期，不要打断当前阶段。

### 你自己要做的事

Agent 能写代码，但这几件事只有你能做：选定视觉方向、确定定价与目标客户、找第一批真实用户试用并收集反馈、审阅法律文本、决定哪些功能不做。越早让真实用户使用，系统就越不会偏离需求。
